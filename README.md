# 家庭调酒酒单小程序

> 不是另一个庞大的公共配方库，而是一个用来管理“属于自己的小酒单”的工具。

市面上的调酒小程序和 App，大多在解决“去哪里找更多配方”以及“如何分享配方”的问题。但今天找到一杯酒并不难：社交平台上每天都有新的配方、教程和灵感。真正麻烦的是，一条内容刷过去后可能再也找不到；临时想喝时，才发现配方需要提前浸泡两天，某瓶酒还要网购，手头的水果却已经快过期。

这个小程序想解决的不是“还有什么酒”，而是：

- 我收藏过哪些真正想喝的酒？
- 这些酒要提前多久准备，需要什么设备？
- 我家里现在有什么，还缺什么？
- 哪些材料今天就该优先用掉？
- 以我当前的环境和材料，哪一杯最适合现在做？

适合人群：

- 在社交平台收藏过不少调酒配方，真正想做时却总要翻很久；
- 家里或宿舍有一个规模不大、但舒适温馨的小吧台；
- 比起浏览上千杯酒，更关心“我今晚到底能做哪一杯”；
- 买过一袋柠檬、一盒薄荷或一瓶果汁，只用了一点，后来才发现它已经悄悄过期；
- 想记住自己喜欢的比例、材料和做法，而不是每次都从头查一遍。

不需要专业设备齐全，也不需要背下一整本鸡尾酒谱。只要你偶尔想给自己做一杯，又希望这件事更有条理一点，就可以从这里开始。

## ✨ 产品亮点

### 1. 🍸 管理自己的小酒单，而不是浏览别人的大酒库

看到喜欢的配方时，可以立即录入酒名、材料、制作方式、步骤和个人评价，建立只属于自己的酒单。以后想重做一杯酒，不必再翻收藏夹、聊天记录和浏览历史。

产品不以社交、点赞或公共配方数量为核心，而是关心一条配方进入个人生活之后，如何被保存、准备和真正做出来。

### 2. 录入一杯酒，不需要反复填写相同材料

金酒、白朗姆、伏特加等常用基酒，以及柠檬汁、糖浆等高频材料已经进入默认材料库。录入配方时可以按“基酒 / 利口酒 / 果汁果蔬 / 混合饮品”快速选择，也可以全库搜索或直接创建新材料。

新建配方时出现的新材料会自动进入个人材料库；提前准备中使用的材料也采用同一套逻辑，不需要之后再重复维护。预调成品、基酒和利口酒还会按更符合调酒阅读习惯的默认顺序展示，用户手动调整后则保留自己的排序。

### 3. ⏱️ 不只记录配方，还记录“什么时候才能做”

配方可以标记为即调、冷冻、冷泡/浸泡、奶洗、低温慢煮或其他，并记录需要提前几小时或几天准备。提前准备产生的混合果汁、浸泡酒等预调成品，可以连同它的详细材料和制作步骤一起保存。

这对家庭调酒尤其重要：宿舍可能没有冰箱，租房可能没有低温慢煮设备，工作日也未必有时间提前两天准备。制作方式和准备时长一目了然，并且可以直接按制作方式筛选；需要的酒杯和工具也会随配方保存，打开详情就能确认当前环境是否满足。

### 4. 🚦 用三种材料状态回答“现在能不能做”

材料不只是简单的“有”或“没有”，而是分成：

- **当前可用**：手头已经有，可以直接制作。
- **随买随用**：暂时没有，但外卖平台或附近超市通常可以买到，购买后即可制作。
- **长期材料缺少**：需要专门购买或等待到货，不能算作今天马上能补齐的材料。

酒单会直接展示缺少的是哪一种状态，也可以按手头材料、随买随用材料和制作条件筛选。材料详情还会告诉用户它被多少杯酒使用，以及买到它可以立即解锁多少杯酒。这样打开酒单时看到的不只是配方，而是这杯酒距离“现在能喝到”还有多远。

### 5. 🍋 鲜材余量和到期提醒，减少家庭调酒浪费

家庭调酒一次通常只会用掉半个柠檬、几片黄瓜或少量果汁。小程序可以记录鲜材的购买日期、剩余量和预计到期日，并在需要关注时提醒。用完后可以快速移出，误操作还可以撤销。

展开一项手头鲜材，就能看到会用到它的个人酒单。推荐顺序会优先考虑：

1. 一杯酒同时命中了多少种手头鲜材；
2. 其他材料是否已经齐全；
3. 配方用量单位是否与记录的余量单位匹配。

因此推荐的不只是“含有黄瓜的酒”，而是更适合当前库存、也更有机会立即做出来的酒。

### 6. 材料分类自带合理默认值，减少无意义的开关

不同材料的使用方式天然不同：基酒通常长期常备，水果通常随买随用并适合追踪保质期，苏打水更接近买来即可使用。小程序会根据材料分类自动填写获取方式、常备状态、默认单位和是否追踪鲜度，用户只在例外时修改。

这套默认逻辑减少了录入过程中的重复点击，同时仍允许每个人按自己的家庭吧台情况调整。

### 7. 保留自己的调酒经验，而不只是原始配方

同一种材料在不同品牌、成熟度或处理方式下可能表现完全不同。材料详情可以持续记录个人观察，例如“这瓶金酒杜松味更重”“这批柠檬偏酸”，记录可以编辑和删除。配方评价则帮助用户区分想尝试、值得复刻和不再考虑的酒。

### 8.  酒精度自动计算

根据液体材料和酒杯容量估算成品体积，并在资料完整时计算预估酒精度。


## 产品原则

- **个人优先**：仅服务自己的收藏和口味。
- **少填一次**：能由分类推断的状态不反复询问，能复用的材料不重复创建。
- **状态可行动**：不只说“缺材料”，还区分能否马上买到、是否需要提前准备。

## v2.0：用喜欢的歌给鸡尾酒起名

### 面向用户：让一杯酒拥有更属于自己的名字

给鸡尾酒起名并不比调出一杯好喝的酒容易。一个名字既要和酒的气质相符，又要足够自然、好记，还最好能承载一点只属于自己的偏好。

v2.0 增加了 AI 智能起名体验：用户可以连接网易云音乐，将红心歌单中的歌曲解析成可复用的歌曲画像。以后录入配方时，点击酒名右侧的“AI 起名”，系统就会从已经解析的歌曲中寻找适合这杯酒的歌名。

起名时，系统会综合理解：

- 配方中的材料及用量，判断谁构成主体、谁只提供少量点缀；
- 提前准备成品在本杯中的用量，以及它内部的材料、批次配比和制作步骤；
- 用户选填的酒液颜色和起名偏好；
- 歌曲表达的主题、情绪、氛围与场景，以及歌名本身是否适合作为酒名。

每次最多推荐 3 个真实存在于用户红心歌单中的歌名，并给出一段自然语言理由。理由不仅说明酒与歌曲为什么匹配，也会带上歌手和歌曲表达。

### 面向开发者与技术爱好者：它是怎么实现的

#### 1. 整体流程

整个功能分成“歌曲预分析”和“酒品即时匹配”两段：

1. 通过官方网易云音乐接口取得红心歌单和歌词；
2. 对每首歌曲调用一次大模型，生成精简的结构化歌曲画像并保存到腾讯云；
3. 用户录入配方并点击 AI 起名时，先让大模型把酒品信息整理成鸡尾酒画像；
4. 使用轻量关键词规则从云端歌曲画像中召回 12 首候选歌曲；
5. 再调用一次大模型比较候选歌曲与鸡尾酒，最终输出最多 3 个歌名和推荐理由。

因此，耗时和 Token 消耗较大的歌词理解发生在歌曲导入阶段。日后反复为不同鸡尾酒起名时，只使用已经保存的精简画像，不会把全部歌词重新发给大模型。

#### 2. 导入数量与重复解析口径

“导入 N 首”表示读取红心歌单按当前顺序排列的**前 N 首**，不是在已有歌曲之后自动新增 N 首。当前 N 的取值范围为 1～300。

例如：

- 第一次导入 200 首，会处理红心歌单前 200 首；
- 再次填写 200，仍然读取前 200 首，不会自动读取第 201～400 首；
- 如果第二次填写 300，在歌单顺序不变的情况下，前 200 首会复用缓存，通常只需新增分析第 201～300 首。

缓存不是只按歌曲 ID 判断，而是综合歌曲来源内容、大模型名称、提示词版本和模型参数生成分析标识。以上信息都没有变化时复用旧画像，不再消耗一次歌曲分析的大模型 Token；歌词或分析配置发生变化时，则会生成新的画像。每首歌曲完成后会立即单独写入云端，中途某一首失败不会导致此前已经完成的画像全部丢失。

#### 3. 一首歌会读取和抽取什么

系统会取得并整理以下歌曲信息：

- 清理后的歌名：只移除标题末尾括号中的 `Live`、`Remix`、`prod. xxx` 等版本标记；
- 歌手名；
- 专辑名和专辑介绍；
- 发行日期：随歌曲元数据保存，供最终推荐理由按需参考，不参与歌曲画像分析；
- 最多 600 个字符的歌词。歌词会先删除时间戳和明确的作词、作曲、制作等署名信息。

大模型输出并保存的核心画像包括：

| 字段 | 含义 |
| --- | --- |
| `summary` | 一句话概括歌曲主要表达 |
| `emotion_keywords` | 0～4 个主要情绪或表达态度 |
| `scene_sensory_keywords` | 0～4 个有歌词依据的场景或感官意象，如时间、空间、颜色、温度、质感和动作 |
| `fitScore` | 0～10 分，只评价歌名这段文字单独作为鸡尾酒名是否自然、易记、有画面，与歌曲内容和热度无关 |
| `namingRisks` | 最多 3 个歌名本身可能存在的命名风险 |

当前提示词优先针对中文说唱语境优化，但导入阶段不会先按音乐类型剔除歌曲。画像只能依据接口实际返回的资料，不会为了补全内容而编造歌词、热度或创作背景。

#### 4. 一杯酒会传入什么

酒品分析会接收饮用时直接加入的材料名称、用量和单位。若配方包含提前准备，还会按层级传入：

- 提前准备成品名称；
- 该成品在本杯中的实际用量；
- 成品内部的原始材料和批次用量；
- 提前准备的制作步骤。

颜色和起名偏好是选填项。材料名称必须沿用用户实际输入：例如柠檬汁和青柠汁不能被替换或统称为“柑橘”，也不能在理由中补出配方里不存在的水果、香料或酒类。

第一轮大模型会将这些信息压缩为鸡尾酒的 `summary`、情绪关键词、场景感官关键词以及希望和避免的命名方向。最终推荐阶段仍会再次收到原始材料和提前准备信息，避免只依赖第一轮概括而丢失具体配方事实。

#### 5. 歌曲与酒如何匹配

当前版本没有使用向量数据库，而是采用“结构化标签召回 + 大模型精排”的两阶段方式：

1. 合并鸡尾酒的情绪关键词和场景感官关键词；
2. 与每首歌曲的两组关键词比较，完全相同记 2 分，互相包含记 1 分；
3. 按关键词匹配分从高到低排序，分数相同时再参考 `fitScore`；
4. 召回前 12 首作为候选；
5. 将候选歌曲的歌名、歌手、发行日期、`summary`、两组关键词和 `fitScore` 交给大模型，输出最多 3 个结果。

最终模型不会再次接收完整歌词，也不会接收全部歌曲画像。推荐理由必须自然提到歌手、吸收歌曲 `summary` 中的核心表达，并结合材料、用量、颜色或偏好说明匹配关系。程序还会把最终名称强制校正为候选歌曲的真实标题，防止模型擅自改写歌名。

#### 6. 后台任务、存储与安全

- 歌曲画像和解析进度保存在腾讯云 CloudBase，并按微信用户隔离；
- 解析任务逐首执行，退出解析页面后仍可由云端定时任务继续处理；
- DeepSeek API Key 的明文只保存在当前设备；为了让后台任务继续运行，云端仅临时保存与用户和任务绑定的加密密文；
- 临时凭证默认有效 6 小时，任务完成或暂停后会从任务记录中移除；
- 单曲失败会记录为失败项，其余歌曲可以继续处理；大模型服务整体异常时任务会暂停，用户可稍后提供有效凭证继续。

#### 7. 当前边界

- 当前只支持读取红心歌单前 N 首，不支持设置起始位置或“自动新增下一批”；
- 单次读取上限为 300 首；
- 不分析音频本身，因此没有使用 BPM、调式、能量值等声音特征；
- 不主动联网搜索歌曲热度和背景，推荐理由中的事实只来自已经取得的歌曲资料；
- 关键词召回适合当前体验版规模，未来歌曲库继续增大后，可以再评估向量检索、混合召回和人工反馈学习。
