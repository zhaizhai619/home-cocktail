# v2.0 思路规划：基于个人歌曲库的鸡尾酒智能起名

> 文档状态：产品思路整理稿<br>
> 本版目标：梳理产品前端流程、歌曲画像、酒品画像与匹配闭环，重点明确 LLM 分析的结构化输出。<br>
> 当前范围：优先从说唱音乐开始验证；网易云音乐数据接入暂采用非官方 API。

## 一、核心思路

歌曲解析速度慢，但解析结果可以长期复用，因此整个功能分为两个阶段：

1. **前期准备阶段**：用户提前导入个人歌曲，由后台逐首清洗、分析并生成歌曲画像。
2. **正式起名阶段**：用户添加酒品时，系统生成酒品画像，只与已经准备好的歌曲画像进行匹配，不再重新分析全部歌曲。

```text
首次准备：
网易云导入 → 歌曲清洗 → LLM 生成歌曲画像 → 存入个人歌曲库

日常起名：
录入酒品 → 生成酒品画像 → 匹配个人歌曲库 → 推荐歌名 → 用户选择或修改
```

这样可以把最慢的工作放在用户正式起名前完成，让“智能起名”按钮在日常使用中尽量快速响应。

## 〇、产品前端设计

### 0.1 酒单页的功能提示入口

在酒单页提供一个可被用户发现、但不强制打断现有使用流程的功能入口，用于介绍：

- 小程序可以根据用户喜欢的歌曲为鸡尾酒智能起名；
- 歌曲需要提前导入和分析；
- 歌曲准备完成后，新增或编辑酒品时即可快速匹配。

入口文案可以表达为“导入我的音乐，解锁智能起名”。用户进入后完成网易云连接、歌曲选择和后台解析。

### 0.2 歌曲导入与解析状态

歌曲解析应当作为后台任务运行，用户可以离开页面，不需要停留等待。前端至少需要表达以下状态：

- 尚未导入；
- 正在导入；
- 正在分析，并显示总体进度；
- 部分歌曲已可用；
- 全部准备完成；
- 部分失败，可重试；
- 歌曲画像需要更新。

产品上不必等全部歌曲分析完成才开放智能起名。只要已经有一部分歌曲画像准备好，就可以先参与匹配，其余歌曲继续在后台处理。

### 0.3 新增酒品时的“智能起名”按钮

在新增或编辑酒品时提供“智能起名”按钮。点击后不再读取和分析全部歌词，而是执行：

1. 根据配方、材料用量和用户补充信息生成酒品画像；
2. 对个人歌曲库中全部成功生成画像的歌曲排序，并选取前列候选；
3. 返回若干个歌名候选，并说明匹配理由；
4. 用户选择一个名称，或在候选名称基础上修改。

如果用户尚未导入歌曲，按钮引导其先建立个人歌曲库；如果只有部分歌曲完成分析，则明确告知本次从已准备好的歌曲中推荐。

### 0.4 个人歌曲库（暂时不做）

建议提供一个简单的个人歌曲库页面，让用户可以：

- 查看已经导入和正在分析的歌曲；
- 查看歌曲原始名称和清洗后用于分析的名称；
- 重新分析失败或结果不理想的歌曲；
- 对明显错误的歌曲画像进行简单纠正；
- 后续补充新的歌单或歌曲。

## 1. 歌曲侧

### 1.1 网易云数据来源

暂定使用：

- [NeteaseCloudMusicApiEnhanced/api-enhanced](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced)

该项目提供用户登录、喜欢的歌曲、歌单、歌曲详情、歌词和专辑内容等非官方接口。

### 1.2 导入什么歌

建议同时支持两种来源，但设置清晰的默认顺序：

1. **默认入口：我喜欢的音乐**<br>
   最能体现“用用户真正喜欢的歌曲命名”，操作也最简单。
2. **可选入口：指定歌单**<br>
   适合用户只想使用说唱歌单，或者希望为不同场景建立不同的候选曲库。

### 1.3 导入多少首

第一版目标为：**最多导入并分析 100 首歌曲**。第一版不在导入阶段根据“是否适合做酒名”剔除歌曲，成功完成画像的歌曲都可以进入后续匹配。

100 首暂时是产品假设，不应被视为固定标准。后续应根据以下结果调整：

- 用户等待时间；
- 单首分析成本；
- 100 首是否足以产生多样化候选；
- 用户实际选择的歌是否集中在较小范围；
- 导入更多歌曲后，推荐质量是否继续提升。

为降低首次等待感，可以采用渐进式准备：先完成一批歌曲便开放功能，其余歌曲继续后台分析。

### 1.4 第一步处理：歌名清洗

送入 LLM 前，只对歌名做必要的技术清洗：当歌名末尾的中文或英文括号中包含 `Live`、`Remix` 或 `prod. 某人` 时，从送给 LLM 的歌名中去掉这部分内容。

原始歌名仍需完整保存，清洗只生成一个新的 `clean_title`，不覆盖网易云返回的原始数据。不能看到括号就全部删除；如果括号内容属于作品标题本身，仍然保留。

### 1.5 为了让 AI 读懂歌曲，需要获取哪些信息

#### 1.5.1 歌名

同时保存原始歌名和清洗后的歌名，不要覆盖原始数据。

```text
原始歌名 → 清洗版本信息 → 保留原名候选 → 可选生成中文意译候选
```

对于“中文歌曲使用英文歌名”的情况，不建议导入阶段强制决定使用英文还是中文翻译，而是同时保留：

- 原始标题；
- 模型推荐用于酒名的版本；
- 推荐理由和置信度。

最终在匹配具体酒品时再决定哪个版本更有氛围，避免提前丢失原名的表达力。

#### 1.5.2 歌手信息

歌手名用于消除同名歌曲歧义，也可以帮助理解作品语境。但模型不得仅根据歌手的常见风格，直接断言某一首歌的具体曲风。

#### 1.5.3 专辑信息

非官方接口中存在专辑内容接口，可以根据专辑 ID 获取专辑及其中歌曲的信息。专辑名称、封面和专辑介绍可以作为歌曲理解的辅助上下文。

但专辑介绍并不一定存在，也不一定包含单曲级介绍，因此处理原则为：

- 获取到有效介绍时作为补充证据；
- 没有介绍时不阻断歌曲分析；
- 专辑信息是定的专辑的概念，可作为一个参考。

#### 1.5.4 歌词

歌词进入 LLM 前需要清洗：

- 去除 LRC 时间戳；
- 去除作词、作曲、编曲、制作人等元数据行；
- 识别并合并机械重复的副歌；
- 尽量避免只截取开头，因为开头可能是 Intro、制作人水印或对白；
- 保留能够体现主题、主要情感和关键意象的部分。

“600 字”可以作为第一版成本控制的实验值，但不建议写死为长期规则。更合理的目标是“在长度限制内保留最有信息量的歌词片段”。歌词较短时可以直接使用完整清洗结果；歌词较长时可先分段理解，再合并歌曲画像。

#### 1.5.5 信息来源对结果的影响

分析时需要区分本次实际使用了哪些信息：

- 仅歌名和歌手；
- 歌名、歌手和歌词；
- 增加了专辑介绍；
- 是否使用人工修正信息。

信息来源会直接影响结果可信度。第一版只把这种差异综合进 `analysis_confidence`，不另外保存详细来源列表；需要排查问题时再查看原始任务记录。

### 1.6 LLM 如何分析歌曲

建议在逻辑上分成两步：

1. **先理解歌曲**：概括歌词在讲什么，以及主要情感、场景和意象。
2. **再提取关键词**：分别生成少量情感关键词和场景/感官关键词。

技术上可以在一次 API 请求中完成。Prompt 只需要明确“先理解、再提取关键词”，不要求模型区分表层情感和深层情感。

### 1.7 歌曲画像的 LLM 输出维度

#### 1.7.1 歌曲在讲什么（一句话）

#### 1.7.2 情感关键词

不再拆分“表层态度”和“深层情感”。模型结合整首歌词，输出 2～4 个最能代表这首歌的情感关键词，例如：孤独、不甘、怀旧、释然、热烈或松弛。

关键词可以同时包含复杂或矛盾的情感，但不额外输出情绪强度、情绪层级和连续分值。

#### 1.7.3 场景与感官关键词

这一组信息承担歌曲与酒品之间的“感官桥梁”，包括：

- 典型场景；
- 时间与季节；
- 空间环境；
- 色彩联想；
- 冷暖感；
- 明暗感；
- 质感联想；
- 反复出现的物体、自然元素、城市元素和动作意象。

模型从中选择 2～4 个最有代表性的关键词。应优先依据歌词中的明确内容；属于推断的联想不能当作歌词事实。

#### 1.7.4 歌名作为酒名的适用性

这一部分与歌曲情绪分析分开，专门判断标题作为鸡尾酒名称是否成立：

- 标题是否可以脱离歌曲独立使用；
- 是否简洁、易记、易展示；
- 是否具有画面感或故事感；
- 原文和中文意译哪个更适合；
- 是否存在歧义、冒犯、敏感或不利于展示的含义；
- 更适合哪类酒品和场景；
- 是否需要轻微去除版本信息，而不是改写作品名称。

这部分的分值和风险只用于具体酒品匹配时的排序、解释和低匹配提示，不生成歌曲的全局“合格/不合格”状态，也不决定歌曲是否进入个人歌曲库或参与匹配。

### 1.8 建议的歌曲画像结构

歌曲画像只保留两组用于匹配的关键词，不再建立表层情感、深层情感、人格气质等独立字段。没有依据时不强行输出。

```json
{
  "song_id": "网易云歌曲ID",
  "raw_title": "原始歌名",
  "clean_title": "清洗后送给LLM的歌名",
  "artist": "歌手",
  "album": "专辑",
  "summary": "用一句话说明这首歌在讲什么",
  "emotion_keywords": ["孤独", "不甘"],
  "scene_sensory_keywords": ["冷感", "城市夜晚"],
  "naming": {
    "preferred_title": "用于酒名的标题版本",
    "fit_score": 0.82,
    "risks": []
  },
  "analysis_confidence": 0.84
}
```

#### 1.8.1 英文字段说明

| 英文字段或取值 | 中文含义 |
|---|---|
| `song_id` | 网易云歌曲 ID |
| `raw_title` | 原始歌名 |
| `clean_title` | 清洗后送给 LLM 的歌名 |
| `artist` / `album` | 歌手 / 专辑 |
| `summary` | 歌曲在讲什么的一句话概括 |
| `emotion_keywords` | 情感关键词，不区分表层和深层 |
| `scene_sensory_keywords` | 场景与感官关键词，包括时间、空间、颜色、冷暖、明暗和质感等联想 |
| `naming` | 歌名作为酒名的相关判断 |
| `preferred_title` | 推荐实际作为酒名的标题 |
| `fit_score` | 歌名适用分，范围 0～1；只用于排序，不剔除歌曲 |
| `risks` | 歧义、敏感或展示风险；没有则为空数组 |
| `analysis_confidence` | 本次歌曲分析的总体置信度 |

歌曲与酒品两侧使用相同的两组关键词结构，后续只需要维护一份简洁的常用词表。

## 2. 酒品侧

### 2.1 酒品侧需要哪些输入

#### 2.1.1 自动获取或从配方中读取

- 材料名称；
- 每种材料的用量；
- 预计酒精度；

#### 2.1.2 用户可以选择填写

- 酒的实际颜色；
- 必要时选择一个最直观的整体感受；
- 可选的命名偏好或想表达的故事。（暂时不做）

### 2.2 材料用量的意义

材料不能只按照“是否出现”判断。用量用于帮助系统理解它在配方中的作用：

- 构成酒体的主体；
- 提供主要风味或气味；
- 负责酸甜平衡；
- 改变质地或视觉；
- 只是少量点缀。

同时不能只看毫升数，因为少量苦精、辣椒、烟熏或高强度利口酒也可能显著改变整杯酒。后续需要结合“相对用量”和“材料影响强度”判断主次。

### 2.3 第一版材料与酒品气质的先验假设

以下内容是编写第一版 Prompt 时的参考，不定义为永远正确的客观事实。实际实现时不需要把每一条都建成独立规则，而是提炼成一段简短的材料联想说明，并通过推荐结果和用户反馈逐步修正。

#### 2.3.1 基酒是一杯酒最底层的基础气质

1. **金酒：清冷、理智、边界感、书卷气**<br>
   金酒以杜松子和草本植物为核心，通常带来干爽、清冽和草本感。
2. **威士忌及陈年深色烈酒：沉稳、阅历、沧桑、硬朗**<br>
   橡木桶、木质、烟熏、焦糖和酒体厚度容易形成更成熟、有重量的联想。
3. **伏特加及白朗姆：亲和、热情、柔软、随和**<br>
   伏特加相对中性，白朗姆常带轻微甘蔗甜感，容易与果味和甜味融合。
4. **龙舌兰：桀骜、随性、辛辣、野蛮生长**<br>
   植物、矿物和辛辣感容易形成个性鲜明、带野性的联想。

#### 2.3.2 其他材料与结构

- **气泡或苏打水**：直给、活泼、外向阳光、清爽；
- **奶制品、百利甜、蛋清等明显改变质地的材料**：柔软、温和、绵密，与单纯清透清新形成不同方向；
- **高糖或复合果味利口酒**：明艳、吸睛、热烈、外放；
- **辛辣材料**：刺激、直接、感官强度高；
- **黄瓜、晴王等材料**：容易形成青绿、清凉、自然、清脆的联想，但仍要结合其他材料和成品颜色判断。

#### 2.3.3 酒体结构

- **短饮、酒精度较高**：干练、犀利、有力量；
- **长饮、气泡**：轻松、亲和、舒展；
- **奶感或厚重酒体**：柔和、浓郁、包裹感；
- **清透、冰冷、草本结构**：克制、清醒、边界感。

### 2.4 颜色与整体气质的第一版假设

- **绿色、浅绿色、透明偏绿**：清新、唯美、自然、冷感；通常不优先匹配攻击性过强的歌曲，但可以容纳轻微忧伤或疏离感；
- **酒红、琥珀、莓色、明显撞色或渐变**：情绪更饱满、视觉刺激更强，可以匹配更强烈或更戏剧化的歌曲；
- 颜色只提供倾向，不能独立决定结果，必须和材料、质地、酒精度及用户补充信息共同判断。

### 2.5 酒品画像的生成方式

实现时，把 2.2～2.4 中的材料、用量、颜色和酒体联想精简后放进 Prompt，作为 LLM 理解鸡尾酒的背景知识。LLM 接收配方和用户填写的信息后，直接生成酒品画像。

Prompt 只需要帮助模型形成大致判断，例如：

- 用量较大的材料通常更影响整体感觉，但少量辛辣、苦精或烟熏材料也可能很突出；
- 金酒通常偏清冷、草本，威士忌偏成熟厚重，气泡偏轻快清爽；
- 奶感材料偏柔和绵密，黄瓜、晴王等容易带来青绿和清凉联想；
- 用户填写的实际颜色优先于根据材料推测的颜色。

这些内容是给模型的参考联想，不要求逐条命中，也不建立复杂的材料规则库、权重表或来源字段。

### 2.6 酒品画像只保留三组结果

1. **一句话描述**：概括整杯酒的整体感觉；
2. **匹配关键词**：与歌曲侧相同，分为情感关键词和场景/感官关键词，每组选择 2～4 个；
3. **命名方向**：说明名字希望呈现和避免的感觉。

例如，黄瓜、晴王和金酒组成的绿色酒，可以得到：

- 情感关键词：平静、松弛；
- 场景/感官关键词：绿色、清爽、夏日、自然。

### 2.7 精简酒品画像结构

```json
{
  "cocktail_id": "酒品ID",
  "summary": "一杯青绿、清爽、克制而温和的酒",
  "main_ingredients": [
    {"name": "金酒", "role": "主体"},
    {"name": "晴王", "role": "主要风味"},
    {"name": "黄瓜", "role": "主要风味"}
  ],
  "emotion_keywords": ["平静", "松弛"],
  "scene_sensory_keywords": ["绿色", "清爽", "夏日", "自然"],
  "naming_direction": {
    "desired": ["简洁", "清新", "有画面感"],
    "avoid": ["过度攻击性", "过度沉重"]
  }
}
```

歌曲和酒品使用相同的两组关键词结构，是让匹配和后期维护保持简单的关键。

## 3. 两者怎么匹配起来

### 3.1 匹配原则

第一版只做“同氛围匹配”：歌曲和酒品在情感、场景或感官联想上相互呼应。互补匹配暂时不做。

### 3.2 第一步：关键词粗排

所有成功生成画像的歌曲都进入排序，不做主观剔除。

系统分别比较两边的 `emotion_keywords` 和 `scene_sensory_keywords`：

- 相同关键词直接增加匹配度；
- 意义接近的关键词获得部分匹配度；
- 歌名适用分作为辅助因素；
- 第一版不提前设计复杂权重公式。

这一阶段从最多 100 首歌曲中选出少量前列候选。

### 3.3 第二步：LLM 复排

把酒品画像和前列歌曲画像交给 LLM，不再发送完整歌词。

LLM 负责：

- 判断哪个歌名最适合这杯酒；
- 处理关键词接近但语义实际冲突的情况；
- 输出三个不同侧重点的候选；
- 为每个候选生成一句推荐理由。

### 3.4 推荐结果

```json
{
  "recommendations": [
    {
      "song_id": "歌曲ID",
      "recommended_name": "推荐酒名",
      "reason": "绿色、清爽的酒品感觉与歌曲的冷感和夏日氛围相呼应"
    }
  ]
}
```

如果候选都不够合适，系统可以提示“当前歌曲库暂时没有特别贴合的名字”，不强行推荐。

## 6. 当前需要确认的问题

1. 情感关键词和场景/感官关键词每组 2～4 个是否合适；
2. 第一批共用关键词词表应该包含哪些词；
3. 材料联想放进 Prompt 后，AI 对酒品整体感觉的判断是否稳定；
4. 每次推荐三个歌名是否符合使用习惯。

这四个问题确认后，再进入 Prompt 和匹配细节的设计。
