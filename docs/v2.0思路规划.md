# v2.0 思路规划：基于个人歌曲库的鸡尾酒智能起名

> 文档状态：产品思路整理稿  
> 本版目标：梳理产品前端流程、歌曲画像、酒品画像与匹配闭环，重点明确 LLM 分析的结构化输出。  
> 当前范围：优先从说唱音乐开始验证；网易云音乐数据接入暂采用非官方 API。

## 一、核心思路

歌曲解析速度慢，但解析结果可以长期复用，因此整个功能分为两个阶段：

1. **低频准备阶段**：用户提前导入个人歌曲，由后台逐首清洗、分析并生成歌曲画像。
2. **高频起名阶段**：用户添加酒品时，系统生成酒品画像，只与已经准备好的歌曲画像进行匹配，不再重新分析全部歌曲。

```text
首次准备：
网易云导入 → 歌曲清洗 → LLM 生成歌曲画像 → 存入个人歌曲库

日常起名：
录入酒品 → 生成酒品画像 → 匹配个人歌曲库 → 推荐歌名 → 用户选择或修改
```

这样可以把最慢的工作放在用户正式起名前完成，让“智能起名”按钮在日常使用中尽量快速响应。

## 〇、产品前端设计

### 0.1 酒单页的功能提示入口

在酒单页提供一个可被用户发现、但不强制打断现有使用流程的功能入口，用于介绍：

- 小程序可以根据用户喜欢的歌曲为鸡尾酒智能起名；
- 歌曲需要提前导入和分析；
- 歌曲准备完成后，新增或编辑酒品时即可快速匹配。

入口文案可以表达为“导入我的音乐，解锁智能起名”。用户进入后完成网易云连接、歌曲选择和后台解析。

### 0.2 歌曲导入与解析状态

歌曲解析应当作为后台任务运行，用户可以离开页面，不需要停留等待。前端至少需要表达以下状态：

- 尚未导入；
- 正在导入；
- 正在分析，并显示总体进度；
- 部分歌曲已可用；
- 全部准备完成；
- 部分失败，可重试；
- 歌曲画像需要更新。

产品上不必等全部歌曲分析完成才开放智能起名。只要已经有一部分歌曲画像准备好，就可以先参与匹配，其余歌曲继续在后台处理。

### 0.3 新增酒品时的“智能起名”按钮

在新增或编辑酒品时提供“智能起名”按钮。点击后不再读取和分析全部歌词，而是执行：

1. 根据配方、材料用量和用户补充信息生成酒品画像；
2. 从个人歌曲库中筛选和排序候选歌曲；
3. 返回若干个歌名候选，并说明匹配理由；
4. 用户选择一个名称，或在候选名称基础上修改。

如果用户尚未导入歌曲，按钮引导其先建立个人歌曲库；如果只有部分歌曲完成分析，则明确告知本次从已准备好的歌曲中推荐。

### 0.4 个人歌曲库

建议提供一个简单的个人歌曲库页面，让用户可以：

- 查看已经导入和正在分析的歌曲；
- 查看某首歌是否参与推荐；
- 手动开启或关闭某首歌；
- 重新分析失败或结果不理想的歌曲；
- 对明显错误的歌曲画像进行简单纠正；
- 后续补充新的歌单或歌曲。

“不参与推荐”应当是一种可恢复的状态，而不是删除歌曲。后续 Prompt、标签体系或用户偏好变化后，可以重新启用。

## 1. 歌曲侧

### 1.1 网易云数据来源

暂定使用：

- [NeteaseCloudMusicApiEnhanced/api-enhanced](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced)

该项目提供用户登录、喜欢的歌曲、歌单、歌曲详情、歌词和专辑内容等非官方接口。它适合用于原型验证，但仍需考虑接口变化、登录状态失效、请求频率、用户 Cookie 安全和后续合规风险。

### 1.2 导入什么歌

建议同时支持两种来源，但设置清晰的默认顺序：

1. **默认入口：我喜欢的音乐**  
   最能体现“用用户真正喜欢的歌曲命名”，操作也最简单。
2. **可选入口：指定歌单**  
   适合用户只想使用说唱歌单，或者希望为不同场景建立不同的候选曲库。

第一版从说唱音乐开始验证时，可以优先鼓励用户选择一个说唱歌单；“我喜欢的音乐”作为更完整但内容更杂的来源保留。

### 1.3 导入多少首

第一版目标为：**筛选后最多保留 100 首参与推荐的歌曲**。

100 首暂时是产品假设，不应被视为固定标准。后续应根据以下结果调整：

- 用户等待时间；
- 单首分析成本；
- 100 首是否足以产生多样化候选；
- 用户实际选择的歌是否集中在较小范围；
- 导入更多歌曲后，推荐质量是否继续提升。

为降低首次等待感，可以采用渐进式准备：先完成一批歌曲便开放功能，其余歌曲继续后台分析。

### 1.4 第一步筛选：标记完全不适合参与推荐的歌曲

筛选分为两层。

#### 1.4.1 规则清洗

先处理不需要大模型判断的技术问题，例如版本后缀、重复记录、缺失歌名以及明显异常的数据。

#### 1.4.2 AI 名称适用性判断

对于主观性较强的情况，不直接删除，而是生成“是否适合做酒名”的判断、置信度和原因。低分歌曲默认不参与推荐，但用户仍可手动开启。

第一版不必提前制定绝对完整的“不适合”标准。可以先分析一批实际歌曲，由人工检查结果，再总结稳定规律。需要避免的是让模型只输出“适合/不适合”而没有原因，否则后续无法调优。

建议至少保留以下结果：

```json
{
  "name_eligibility": "eligible",
  "name_fit_score": 0.82,
  "exclusion_reasons": [],
  "confidence": 0.88
}
```

其中 `name_eligibility` 可以取：

- `eligible`：适合参与推荐；
- `conditional`：在部分酒品或场景下适合；
- `ineligible`：默认不参与推荐；
- `uncertain`：信息不足，等待人工确认。

### 1.5 为了让 AI 读懂歌曲，需要获取哪些信息

#### 1.5.1 歌名

同时保存原始歌名和清洗后的歌名，不要覆盖原始数据。

```text
原始歌名 → 清洗版本信息 → 保留原名候选 → 可选生成中文意译候选
```

需要清理的内容包括但不限于：

- Live；
- Remix；
- Instrumental；
- Radio Edit；
- Demo；
- `prod. xxx`；
- 纯版本说明或平台附加信息。

对于“中文歌曲使用英文歌名”的情况，不建议导入阶段强制决定使用英文还是中文翻译，而是同时保留：

- 原始标题；
- 中文意译标题；
- 模型推荐用于酒名的版本；
- 推荐理由和置信度。

最终在匹配具体酒品时再决定哪个版本更有氛围，避免提前丢失原名的表达力。

#### 1.5.2 歌手信息

歌手名用于消除同名歌曲歧义，也可以帮助理解作品语境。但模型不得仅根据歌手的常见风格，直接断言某一首歌的具体曲风。

#### 1.5.3 专辑信息

非官方接口中存在专辑内容接口，可以根据专辑 ID 获取专辑及其中歌曲的信息。专辑名称、封面和专辑介绍可以作为歌曲理解的辅助上下文。

但专辑介绍并不一定存在，也不一定包含单曲级介绍，因此处理原则为：

- 获取到有效介绍时作为补充证据；
- 没有介绍时不阻断歌曲分析；
- 不把营销文案直接当作歌曲真实主题；
- 专辑信息与歌词冲突时，以歌词内容为主要依据。

#### 1.5.4 歌词

歌词进入 LLM 前需要清洗：

- 去除 LRC 时间戳；
- 去除作词、作曲、编曲、制作人等元数据行；
- 识别并合并机械重复的副歌；
- 尽量避免只截取开头，因为开头可能是 Intro、制作人水印或对白；
- 保留能够体现主题、态度、深层情绪和关键意象的部分。

“600 字”可以作为第一版成本控制的实验值，但不建议写死为长期规则。更合理的目标是“在长度限制内保留最有信息量的歌词片段”。歌词较短时可以直接使用完整清洗结果；歌词较长时可先分段理解，再合并歌曲画像。

#### 1.5.5 信息来源记录

每个歌曲画像都应记录本次分析实际使用了哪些信息：

- 仅歌名和歌手；
- 歌名、歌手和歌词；
- 增加了专辑介绍；
- 是否使用人工修正信息。

信息来源会直接影响结果可信度，应与分析置信度一起保存。

### 1.6 LLM 如何分析歌曲

建议在逻辑上分成两步：

1. **先理解歌曲**：概括故事、态度、深层情绪、矛盾、场景和意象。
2. **再映射标签**：把理解结果转换成受控标签和连续分值。

技术上可以在一次 API 请求中完成，但 Prompt 必须明确先理解、后归类。这样当结果错误时，可以区分是“理解错了歌词”，还是“标签映射不合理”。

### 1.7 歌曲画像的 LLM 输出维度

#### 1.7.1 歌曲在讲什么

- **表层叙事**：歌词直接讲述的人、事和情境；
- **核心主题**：整首歌持续围绕的主要议题；
- **叙事视角**：第一人称自述、对某人说话、群体表达、角色扮演等；
- **情绪或叙事走向**：从什么状态发展到什么状态；
- **核心矛盾或诉求**：主人公真正想得到、摆脱、证明或保护的东西。

#### 1.7.2 演唱者表现出来的态度

这里描述的是歌曲对外呈现的姿态，而不是直接等同于深层情绪。例如自信、挑衅、克制、戏谑、疏离、坦诚或讨好。

对说唱音乐尤其需要区分：

- 演唱者本人和歌词中的叙事角色；
- 表面的炫耀和深层的渴望认可；
- 脏话与真正的愤怒；
- 高能量表达与正面情绪；
- 反讽、夸张、双关和黑色幽默。

#### 1.7.3 更深层的情绪

除了表面态度，还要识别可能持续支撑整首歌的情绪和心理动力，例如不甘、孤独、怀旧、渴望认可、失控、释然、依恋或自我保护。

建议同时输出：

- 主导深层情绪；
- 次要或混合情绪；
- 情绪效价 `valence`；
- 情绪唤醒度 `arousal`；
- 情绪强度；
- 情绪复杂度或矛盾程度。

#### 1.7.4 场景与感官意象

这一组信息承担歌曲与酒品之间的“感官桥梁”，包括：

- 典型场景；
- 时间与季节；
- 空间环境；
- 色彩联想；
- 冷暖感；
- 明暗感；
- 质感联想；
- 反复出现的物体、自然元素、城市元素和动作意象。

模型应优先依据歌词中的明确内容；属于推断的联想必须降低置信度，不能把主观想象伪装成歌词事实。

#### 1.7.5 人格与社交气质

用于表达歌曲给人的整体人物感和互动方式，例如：

- 内敛或外放；
- 亲和或疏离；
- 温柔或锋利；
- 克制或放纵；
- 理性或感性；
- 成熟或少年感；
- 顺从或反叛。

这些维度主要服务于酒品人格匹配，不用于判断歌手本人的真实性格。

#### 1.7.6 说唱风格信息

在只有歌名、歌手和歌词、没有音频及可靠外部资料时，模型不能稳定判断 Trap、Drill、Boom bap 等具体曲风。

因此第一版应当：

- 允许曲风输出 `unknown`；
- 单独输出曲风判断依据和置信度；
- 不把低置信度曲风作为核心匹配条件；
- 不要求模型猜测 BPM、Flow、Beat、808 或真实编曲质感；
- 后续可以通过人工修正、可靠元数据或合法音频分析补充。

#### 1.7.7 歌名作为酒名的适用性

这一部分与歌曲情绪分析分开，专门判断标题作为鸡尾酒名称是否成立：

- 标题是否可以脱离歌曲独立使用；
- 是否简洁、易记、易展示；
- 是否具有画面感或故事感；
- 原文和中文意译哪个更适合；
- 是否存在歧义、冒犯、敏感或不利于展示的含义；
- 更适合哪类酒品和场景；
- 是否需要轻微去除版本信息，而不是改写作品名称。

#### 1.7.8 可靠性与可追溯性

所有重要判断都需要同时输出：

- 总体置信度；
- 具体维度的置信度；
- 使用的信息来源；
- 无法判断的字段；
- 是否存在歌词歧义；
- 是否需要人工确认；
- Prompt 版本和标签体系版本。

### 1.8 建议的歌曲画像结构

以下结构用于说明输出边界，字段名称后续可以在技术设计阶段调整：

```json
{
  "song_id": "网易云歌曲ID",
  "raw_title": "原始歌名",
  "clean_title": "清洗后的原名",
  "translated_title": "可选中文意译",
  "recommended_title_form": "original | translated | either",
  "artist": "歌手",
  "album": "专辑",
  "understanding": {
    "surface_story": "表层叙事摘要",
    "core_themes": ["主题1", "主题2"],
    "narrative_perspective": "叙事视角",
    "emotional_arc": "情绪或叙事走向",
    "core_tension_or_need": "核心矛盾或诉求"
  },
  "expression": {
    "surface_attitudes": ["态度1", "态度2"],
    "underlying_emotions": ["深层情绪1", "深层情绪2"],
    "valence": 0.2,
    "arousal": 0.7,
    "emotion_intensity": 0.8,
    "emotional_complexity": 0.6
  },
  "sensory_bridge": {

    "brightness": "dark | muted | neutral | bright",
    "textures": ["质感"],
    "imagery": ["关键意象"]
  },
  "persona": {
    "traits": ["整体人格气质"],
    "social_energy": "introverted | balanced | extroverted",
    "edge": "soft | restrained | sharp | aggressive"
  },
  "rap_style": {
    "label": "unknown",
    "basis": [],

  },
  "naming": {
    "eligibility": "eligible | conditional | ineligible | uncertain",
    "fit_score": 0.82,
    "preferred_title": "用于酒名的标题版本",
    "title_qualities": ["简洁", "有画面感"],
    "risks": [],
    "explanation_only_suitable_cocktail_directions": ["适合的酒品方向"]
  },
  "reliability": {
    "overall_confidence": 0.84,
    "sources_used": ["title", "artist", "lyrics", "album_description"],
    "unknown_fields": ["具体说唱流派"],
    "needs_human_review": false,
    "prompt_version": "song-profile-v1",
    "taxonomy_version": "v1"
  },
  "provenance": [
    {
      "field": "sensory_bridge.colors[0]",
      "source_type": "lyric_observation",
      "source_ref": "lyrics",
      "confidence": 0.9
    },
    {
      "field": "persona.traits",
      "source_type": "llm_inference",
      "source_ref": "lyrics_and_album_description",
      "confidence": 0.72
    }
  ]

```

其中 `provenance` 用于记录字段级来源，避免只知道“整首歌用了歌词”，却不知道某个颜色、人格或意象究竟来自歌词事实还是模型联想。数组内不同值来源不同时，`field` 应具体指向数组项；如果整个数组共享同一来源，才允许只记录数组字段本身。

歌曲侧建议使用的 `source_type` 包括：

- `title_observation`：直接来自歌名；
- `lyric_observation`：直接来自歌词；
- `album_observation`：直接来自专辑信息；
- `artist_prior`：依据歌手背景形成的弱先验；
- `llm_inference`：模型综合推断或联想；
- `human_correction`：经过用户人工修正。

“适合哪类酒品”只作为解释和人工观察字段，不直接参与第一版匹配得分，避免先由模型猜一次适合的酒，再用这个猜测反过来决定匹配结果。

## 2. 酒品侧

### 2.1 酒品侧需要哪些输入

#### 2.1.1 自动获取或从配方中读取

- 材料名称；
- 每种材料的用量；
- 材料类别；
- 预计总液体量；
- 预计酒精度；
- 是否含气泡；
- 是否包含奶制品、蛋清等明显影响质感的材料；
- 短饮或长饮等已有配方信息。

#### 2.1.2 用户可以选择填写

- 酒的实际颜色；
- 必要时选择一个最直观的整体感受；
- 可选的命名偏好或想表达的故事。

颜色适合让用户选择填写，因为材料颜色不一定等于最终成品颜色。用户实际填写的信息优先级高于系统推断。

### 2.2 材料用量的意义

材料不能只按照“是否出现”判断。用量用于帮助系统理解它在配方中的作用：

- 构成酒体的主体；
- 提供主要风味或气味；
- 负责酸甜平衡；
- 改变质地或视觉；
- 只是少量点缀。

同时不能只看毫升数，因为少量苦精、辣椒、烟熏或高强度利口酒也可能显著改变整杯酒。后续需要结合“相对用量”和“材料影响强度”判断主次。

### 2.3 第一版材料与酒品气质的先验假设

以下内容作为第一版 Prompt 和规则库的初始假设，不定义为永远正确的客观事实。后续应通过实际推荐结果和用户反馈修正。

#### 2.3.1 基酒是一杯酒最底层的基础气质

1. **金酒：清冷、理智、边界感、书卷气**  
   金酒以杜松子和草本植物为核心，通常带来干爽、清冽和草本感。
2. **威士忌及陈年深色烈酒：沉稳、阅历、沧桑、硬朗**  
   橡木桶、木质、烟熏、焦糖和酒体厚度容易形成更成熟、有重量的联想。
3. **伏特加及白朗姆：亲和、热情、柔软、随和**  
   伏特加相对中性，白朗姆常带轻微甘蔗甜感，容易与果味和甜味融合。
4. **龙舌兰：桀骜、随性、辛辣、野蛮生长**  
   植物、矿物和辛辣感容易形成个性鲜明、带野性的联想。

#### 2.3.2 其他材料与结构

- **气泡或苏打水**：直给、活泼、外向阳光、清爽；
- **奶制品、百利甜、蛋清等明显改变质地的材料**：柔软、温和、绵密，与单纯清透清新形成不同方向；
- **高糖或复合果味利口酒**：明艳、吸睛、热烈、外放；
- **辛辣材料**：刺激、直接、高唤醒度；
- **黄瓜、青葡萄等材料**：容易形成青绿、清凉、自然、清脆的联想，但仍要结合其他材料和成品颜色判断。

#### 2.3.3 酒体结构

- **短饮、酒精度较高**：干练、犀利、有力量；
- **长饮、气泡、较低酒精度**：轻松、亲和、舒展；
- **奶感或厚重酒体**：柔和、浓郁、包裹感；
- **清透、冰冷、草本结构**：克制、清醒、边界感。

### 2.4 颜色与整体气质的第一版假设

- **绿色、浅绿色、透明偏绿**：清新、唯美、自然、冷感；通常不优先匹配攻击性过强的歌曲，但可以容纳轻微忧伤或疏离感；
- **酒红、琥珀、莓色、明显撞色或渐变**：情绪更饱满、视觉刺激更强，可以匹配更强烈或更戏剧化的歌曲；
- 颜色只提供倾向，不能独立决定结果，必须和材料、质地、酒精度及用户补充信息共同判断。

### 2.5 酒品画像的生成方式

酒品画像不建议完全依赖一个自由发挥的 Prompt。更稳妥的方式是：

1. 材料规则库先提供每种材料的基础感官和气质信息；
2. 系统根据用量和材料影响强度判断主体、支撑和点缀；
3. 用户填写的颜色或整体感受覆盖相冲突的系统推断；
4. LLM 综合这些结构化事实，生成整杯酒的统一画像；
5. LLM 必须说明哪些结论来自配方，哪些属于联想，避免无依据发挥。

### 2.6 酒品画像的输出维度

为了能与歌曲画像匹配，酒品侧应尽量输出相同或可映射的维度：

- 酒品的一句话整体描述；
- 主导材料、支撑材料和点缀材料；
- 整体人格气质；
- 情绪方向和唤醒度区间；
- 冷暖、明暗、颜色和视觉强度；
- 清透、气泡、绵密、厚重等质感；
- 温柔、克制、锋利、刺激或攻击性；
- 适合的场景、时间和季节；
- 材料自然产生的核心意象；
- 推荐名称应该具有的气质；
- 应避免的名称方向；
- 每个判断的来源和置信度。

## 3. 两者怎么匹配起来

### 3.1 匹配原则

第一版以“同氛围匹配”为主：歌曲和酒品在情绪、人格、视觉、质感或意象上形成一致或相互呼应的感觉。

“互补匹配”可以作为后续玩法，例如用柔和歌曲命名辛辣烈酒，但它的解释难度更高，第一版暂不作为默认逻辑。

### 3.2 两侧画像的统一匹配契约

歌曲画像和酒品画像不能只做到“字段看起来相似”，还需要规定哪些字段真正参与比较、取值范围是否一致，以及缺失数据如何处理。

#### 3.2.1 第一版共同匹配字段

| 匹配概念 | 歌曲侧 | 酒品侧 | 统一规则 |
|---|---|---|---|
| 情绪效价 | `expression.valence` 单点，-1～1 | `expression.target_valence` 目标区间，-1～1 | 歌曲落在区间内视为充分匹配，区间外按归一化距离衰减 |
| 唤醒度 | `expression.arousal` 单点，0～1 | `expression.target_arousal` 目标区间，0～1 | 与效价使用相同的区间距离规则 |
| 情绪强度 | `expression.emotion_intensity`，0～1 | `expression.emotion_intensity`，0～1 | 比较绝对距离 |
| 冷暖 | `sensory_bridge.temperature` | `sensory_bridge.temperature` | 使用同一受控枚举和顺序 |
| 明暗 | `sensory_bridge.brightness` | `sensory_bridge.brightness` | 使用同一受控枚举和顺序 |
| 色彩 | `sensory_bridge.colors` | `sensory_bridge.color_family` | 映射到同一受控色彩族；相同色彩强匹配，相邻或兼容色彩按关系表给补充分 |
| 人格锋利度 | `persona.edge` | `persona.edge` | 使用同一受控枚举和顺序 |
| 社交能量 | `persona.social_energy` | `persona.social_energy` | 使用同一受控枚举 |
| 场景 | `sensory_bridge.scenes` | `sensory_bridge.scenes` | 仅使用受控标签比较重合度 |
| 时间与季节 | `sensory_bridge.time_and_season` | `sensory_bridge.time_and_season` | 仅使用受控标签比较重合度 |
| 质感 | `sensory_bridge.textures` | `sensory_bridge.textures` | 仅使用受控标签或明确的兼容关系 |
| 意象 | `sensory_bridge.imagery` | `sensory_bridge.imagery` | 受控标签重合为主，语义相近只作补充分 |
| 名称适用性 | `naming.eligibility`、`naming.fit_score` | `naming_direction` | 先做资格过滤，再判断名称气质是否符合酒品需求 |

具体词表和权重仍可以通过测试确定，但同一 `taxonomy_version` 下，两侧必须使用相同枚举、同一数值范围和同一含义。

#### 3.2.2 第一版受控枚举示意

- `temperature`：`cold | cool | neutral | warm | hot`；
- `brightness`：`dark | muted | neutral | bright`；
- `edge`：`soft | restrained | sharp | aggressive`；
- `social_energy`：`introverted | balanced | extroverted`。

其他用于匹配的标签也应来自版本化受控词表。LLM 可以在解释文本里自由描述，但不能把临时创造的自由词直接加入结构化打分。

#### 3.2.3 缺失值和不确定性的统一规则

- `null` 表示没有足够信息，不能当成中性或 0；
- 空数组 `[]` 表示该字段已经分析，但没有识别到符合受控词表的标签；
- 数值 0 表示真实的坐标或强度值，不表示缺失；
- 置信度过低的字段不进入粗排，只能用于解释或等待人工确认；
- 用户明确填写和人工修正的字段优先级最高；
- 两侧 `taxonomy_version` 不一致时，应先迁移或重新生成画像，不能直接比较。

#### 3.2.4 参与打分与只用于解释的字段

只有共同契约内、来源可追踪且置信度达到要求的字段参与结构化粗排。以下内容第一版只用于解释，不直接计分：

- 自由文本摘要；
- 未进入受控词表的开放联想；
- 低置信度说唱流派；
- 歌曲画像中模型猜测的“适合哪类酒品”；
- 缺少事实依据的人格延伸描述。

### 3.3 匹配分层

#### 3.3.1 第一步：硬性过滤

排除：

- 默认不参与推荐的歌曲；
- 名称存在明显风险的歌曲；
- 用户手动关闭的歌曲；
- 数据不足且置信度过低的歌曲；
- 与用户当前语言偏好冲突且没有合适标题版本的歌曲。

#### 3.3.2 第二步：结构化粗排

使用已经保存的歌曲画像和酒品画像进行快速计算，比较：

- 情绪方向与强度；
- 人格气质；
- 冷暖、明暗和质感；
- 场景与意象；
- 歌名作为酒名的适用性。

具体权重暂不在本阶段写死，应通过第一批实际歌曲和酒品测试确定。

#### 3.3.3 第三步：候选复排

从粗排结果中取少量候选，让 LLM 结合酒品画像、歌曲画像和歌名适用性完成最终复排。

此时不需要把 100 首歌曲的完整歌词再次发给模型，只需要提供候选歌曲的结构化画像。LLM 的职责是：

- 判断哪几个歌名最能代表这杯酒；
- 在原名和中文意译之间选择；
- 识别结构化打分没有处理好的语义冲突；
- 生成简短、可理解的推荐理由。

### 3.4 推荐结果

建议每次输出若干个不同侧重点的候选，而不是只给唯一答案。例如：

- 最贴合整体氛围；
- 最贴合材料或颜色意象；
- 最有故事感或最适合作为酒名。

每个候选至少展示：

- 推荐歌名；
- 歌手；
- 使用原名还是中文意译；
- 一句话推荐理由；
- 主要匹配点；
- 必要时提示匹配置信度。

### 3.5 匹配输出示意

```json
{
  "cocktail_id": "酒品ID",
  "recommendations": [
    {
      "song_id": "歌曲ID",
      "recommended_name": "用于酒名的歌名",
      "title_form": "original",
      "rank": 1,
      "match_summary": "青绿、清冷的视觉和歌曲中夏夜微风的意象形成呼应",
      "matched_aspects": ["颜色", "温度", "场景意象", "克制感"],
      "conflicts": [],
      "confidence": 0.86
    }
  ],
  "matching_version": "cocktail-song-match-v1"
}
```

### 3.6 没有合适结果时的处理

系统不应为了给出答案而强行推荐。以下情况可以提示用户补充信息、扩大歌曲库或直接使用普通命名：

- 可参与推荐的歌曲太少；
- 酒品画像置信度过低；
- 候选歌名都存在明显冲突；
- 用户填写的信息与配方推断严重矛盾；
- 最高匹配结果仍低于最低可接受标准。

## 4. 用户反馈与迭代闭环

### 4.1 需要记录的用户反馈

- 用户最终选择了哪一个推荐名称；
- 用户跳过了哪些名称；
- 用户是否采用中文意译；
- 用户是否修改了推荐名称；
- 用户是否认为某首歌不应该参与推荐；
- 用户是否纠正了歌曲或酒品画像。

### 4.2 为什么反馈闭环是必要的

推荐效果不好可能来自不同环节：

- 歌词清洗丢失了关键信息；
- LLM 没有正确理解歌曲；
- 标签体系表达能力不足；
- 材料到酒品气质的映射不合理；
- 匹配权重不合理；
- 歌曲与酒确实相似，但歌名不适合作为酒名。

只有记录中间画像和最终选择，才能定位需要调整的是 Prompt、规则库还是匹配逻辑。

### 4.3 第一版评测方法

建议先建立一个小型人工标准集：

1. 选择一批自己非常熟悉、差异明显的说唱歌曲；
2. 人工填写它们的表层叙事、态度、深层情绪、意象和名称适用性；
3. 比较不同 Prompt 版本的输出；
4. 准备一批代表性的鸡尾酒；
5. 检查正确歌曲是否进入推荐前列；
6. 记录自己是否愿意真的使用推荐歌名。

核心指标不只是“标签看起来是否正确”，还包括：

- 推荐结果中是否出现明显不合适的名称；
- 合适候选进入前几名的比例；
- 用户最终采用推荐名称的比例；
- 用户需要手动修改的比例；
- 不同 Prompt 版本下结果是否稳定。

## 5. 当前需要继续验证的问题

1. 第一版默认导入“我喜欢的音乐”还是优先引导选择说唱歌单；
2. 100 首是否在等待成本和候选丰富度之间达到平衡；
3. “完全不适合做酒名”的稳定判断标准；
4. 歌词应如何截取或压缩，才能兼顾成本和理解准确度；
5. 原始英文标题与中文意译标题的选择规则；
6. 第一版歌曲标签受控词表；
7. 第一版材料规则库及材料影响强度；
8. 歌曲与酒品各维度的匹配权重；
9. 最低可接受匹配分数；
10. 用户纠正结果如何反哺歌曲画像和匹配规则。

## 6. 当前阶段结论

第一版不需要让 LLM 在每次起名时重新阅读 100 首歌曲，也不需要先建立复杂的知识库。核心做法是：

1. 提前异步生成并保存个人歌曲画像；
2. 根据材料、用量和用户填写信息生成酒品画像；
3. 用相同的感官、情绪、人格和意象语言连接两侧；
4. 先结构化粗排，再让 LLM 复排少量候选；
5. 保存用户选择和纠正，持续校准 Prompt、标签体系和匹配逻辑。

这套结构优先解决“等待时间长”“标签难比较”“推荐理由不可解释”和“Prompt 无法评测”四个核心问题。
