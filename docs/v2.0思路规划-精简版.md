# v2.0 思路规划（精简版）

> 目标：根据用户喜欢的歌曲，为鸡尾酒推荐一个有个人意义、与酒品气质相符的歌名。<br>
> 第一版范围：网易云歌曲导入、歌曲预分析、酒品画像、快速匹配；优先用说唱歌曲测试效果。

## 一页结论

整个功能只保留三个核心对象：

1. **歌曲画像**：一句话理解歌曲，再生成少量匹配标签。
2. **酒品画像**：根据材料、用量和颜色，生成一句话描述和少量匹配标签。
3. **匹配结果**：先按标签选出前列歌曲，再让 LLM 从少量候选中推荐三个歌名。

```text
提前准备：
导入歌曲 → 后台逐首分析 → 保存歌曲画像

日常起名：
录入酒品 → 生成酒品画像 → 标签粗排 → LLM 复排 → 推荐三个歌名
```

第一版不建立复杂知识库，不分析音频曲风，也不设置大量独立维度。

## 0. 产品前端设计

### 0.1 酒单页提示入口

在酒单页提供一个入口，例如“导入我的音乐，解锁智能起名”。

用户进入后：

1. 连接网易云；
2. 选择“我喜欢的音乐”或指定歌单；
3. 导入歌曲；
4. 系统在后台逐首分析；
5. 已经分析完成的歌曲可以立即参与起名，其余歌曲继续处理。

前端显示简单进度，例如“已完成 28/100 首”。用户可以离开页面，不需要一直等待。

### 0.2 添加酒品时的智能起名

新增或编辑酒品时提供“智能起名”按钮。

此时歌曲已经提前完成分析，所以按钮点击后只需要：

1. 生成当前酒品画像；
2. 与个人歌曲库进行匹配；
3. 返回三个候选歌名和简短理由。

## 1. 歌曲侧

### 1.1 导入范围

- 来源支持“我喜欢的音乐”和指定歌单；
- 第一版最多导入并分析 100 首；
- 第一版不判断歌曲是否“有资格”做酒名，也不提前剔除歌曲；
- 所有成功生成画像的歌曲都进入后续匹配排序。

### 1.2 歌名清洗

完整保存网易云返回的原始歌名。

送给 LLM 前，如果歌名末尾括号中包含以下内容，只删除对应的括号后缀：

- `Live`；
- `Remix`；
- `prod. 某人`。

其他括号内容不处理，避免误删作品标题的一部分。

### 1.3 给 LLM 的歌曲信息

第一版提供：

- 清洗后的歌名；
- 歌手；
- 专辑名称；
- 有则提供专辑介绍；
- 清洗后的歌词片段。

歌词去掉时间戳、作词和制作人员等元数据。歌词长度暂以约 600 字作为实验值，后续根据实际准确度调整。

### 1.4 歌曲只分析三组结果

#### A. 歌曲理解

- 用一句话说明这首歌在讲什么；
- 不展开复杂的叙事结构。

#### B. 匹配标签

从四类中选择最有代表性的标签，总数控制在 5～8 个：

| 标签类型 | 表达什么 | 示例 |
|---|---|---|
| 情绪 | 歌曲更深层的感受 | 孤独、松弛、不甘、热烈 |
| 气质 | 歌曲对外呈现的态度和人格 | 克制、疏离、温柔、反叛 |
| 感官 | 能与酒的颜色和口感形成联系的感觉 | 冷感、明亮、粗粝、绵密 |
| 场景 | 歌曲最有代表性的时间、空间或意象 | 城市夜晚、夏日、雨、霓虹 |

模型没有足够依据时不输出该标签，不能为了凑满数量而编造。

#### C. 歌名信息

- 推荐实际用于酒名的标题；
- 歌名作为酒名的适用分；
- 可能存在的歧义、敏感或展示风险。

适用分只参与排序，不用于剔除歌曲。

### 1.5 精简歌曲画像 JSON

```json
{
  "song_id": "网易云歌曲ID",
  "raw_title": "原始歌名",
  "clean_title": "清洗后送给LLM的歌名",
  "artist": "歌手",
  "summary": "一句话说明这首歌在讲什么",
  "match_tags": [
    {"type": "emotion", "value": "孤独"},
    {"type": "personality", "value": "克制"},
    {"type": "sensory", "value": "冷感"},
    {"type": "scene", "value": "城市夜晚"}
  ],
  "naming": {
    "preferred_title": "推荐用于酒名的标题",
    "fit_score": 0.82,
    "risks": []
  },
  "analysis_confidence": 0.84
}
```

英文字段含义：

| 英文字段 | 中文含义 |
|---|---|
| `song_id` | 网易云歌曲 ID |
| `raw_title` | 原始歌名 |
| `clean_title` | 清洗后送给 LLM 的歌名 |
| `artist` | 歌手 |
| `summary` | 歌曲的一句话理解 |
| `match_tags` | 用于歌曲与酒品匹配的标签 |
| `type` | 标签类型 |
| `value` | 标签内容 |
| `emotion` | 情绪标签 |
| `personality` | 气质标签 |
| `sensory` | 感官标签 |
| `scene` | 场景标签 |
| `naming` | 歌名相关判断 |
| `preferred_title` | 推荐实际作为酒名的标题 |
| `fit_score` | 歌名适用分，范围 0～1 |
| `risks` | 歌名可能存在的风险，没有则为空数组 |
| `analysis_confidence` | 本次歌曲分析的总体置信度 |

## 2. 酒品侧

### 2.1 输入信息

自动从酒品配方中读取：

- 材料；
- 每种材料的用量；
- 预计酒精度。

用户可以选择填写酒的实际颜色。颜色没有填写时，系统可以根据材料推测，但不能覆盖用户填写的实际颜色。

### 2.2 材料和用量怎么使用

材料不是出现了就同等重要。系统需要结合用量和材料本身的影响强度，判断哪些是：

- 主体；
- 主要风味；
- 质感或颜色来源；
- 少量点缀。

例如少量辣椒或苦精也可能影响明显，不能只按照毫升数排序。

材料规则库只负责给 LLM 提供基础常识，例如：

| 材料或结构 | 初始联想 |
|---|---|
| 金酒 | 清冷、理智、草本、克制 |
| 威士忌或陈年深色烈酒 | 沉稳、成熟、木质、硬朗 |
| 伏特加或白朗姆 | 亲和、随和、容易与其他风味融合 |
| 龙舌兰 | 桀骜、直接、植物感、辛辣 |
| 气泡或苏打水 | 活泼、清爽、外向 |
| 奶制品、百利甜或蛋清 | 柔软、温和、绵密 |
| 高糖或复合果味利口酒 | 明艳、热烈、外放 |
| 高酒精度短饮 | 干练、犀利、有力量 |

这些是第一版先验，不是固定真理，后续根据实际反馈调整。

### 2.3 酒品也只生成三组结果

#### A. 酒品理解

用一句话概括这杯酒的整体感觉。

#### B. 匹配标签

使用与歌曲完全相同的四类标签：情绪、气质、感官和场景，总数同样控制在 5～8 个。

例如一杯黄瓜、阳光玫瑰和金酒组成的绿色酒，可以得到：

- 情绪：平静；
- 气质：克制、温和；
- 感官：绿色、清爽、冷感；
- 场景：夏日、自然。

#### C. 命名方向

只说明这杯酒希望名字呈现的感觉，例如简洁、清新、有画面感，以及应该避免的方向。

### 2.4 精简酒品画像 JSON

```json
{
  "cocktail_id": "酒品ID",
  "summary": "一杯青绿、清爽、克制而温和的酒",
  "main_ingredients": [
    {"name": "金酒", "role": "主体"},
    {"name": "阳光玫瑰", "role": "主要风味"},
    {"name": "黄瓜", "role": "主要风味"}
  ],
  "match_tags": [
    {"type": "emotion", "value": "平静"},
    {"type": "personality", "value": "克制"},
    {"type": "sensory", "value": "绿色"},
    {"type": "sensory", "value": "清爽"},
    {"type": "scene", "value": "夏日"}
  ],
  "naming_direction": {
    "desired": ["简洁", "清新", "有画面感"],
    "avoid": ["过度攻击性", "过度沉重"]
  }
}
```

歌曲和酒品使用相同的 `match_tags` 结构，是后续匹配能够保持简单的关键。

## 3. 两者怎么匹配

### 3.1 第一步：标签粗排

所有成功生成画像的歌曲都进入排序，不做歌曲剔除。

系统比较歌曲与酒品的 `match_tags`：

- 相同标签直接增加匹配度；
- 意义接近的标签可以获得部分匹配度；
- 不同类别可以设置简单权重，但第一版不提前设计复杂公式；
- 歌名适用分只作为辅助排序因素。

这一阶段从最多 100 首歌曲中选出前列候选。

### 3.2 第二步：LLM 复排少量候选

把酒品画像和前列歌曲画像交给 LLM，不再发送完整歌词。

LLM 负责：

- 综合判断哪个歌名最适合这杯酒；
- 处理标签相近但实际语义不合适的情况；
- 输出三个不同侧重点的候选；
- 为每个候选生成一句简短理由。

### 3.3 推荐结果

```json
{
  "recommendations": [
    {
      "song_id": "歌曲ID",
      "recommended_name": "推荐酒名",
      "reason": "绿色、清爽的酒品感觉与歌曲的冷感和夏日氛围相呼应"
    }
  ]
}
```

如果候选都不够合适，系统可以明确提示“当前歌曲库暂时没有特别贴合的名字”，不强行推荐。

## 4. Prompt 与后续调整

### 4.1 Prompt 的重点

歌曲 Prompt 只需要稳定完成三件事：

1. 正确理解歌曲在讲什么；
2. 从共用词表中选择 5～8 个最有代表性的标签；
3. 判断歌名作为酒名的表现。

酒品 Prompt 同样只完成三件事：

1. 判断材料在配方中的主次作用；
2. 生成与歌曲侧共用的 5～8 个标签；
3. 给出命名方向。

### 4.2 第一版只维护两个东西

后续主要维护：

1. **共用标签词表**：哪些标签保留、合并或新增；
2. **材料规则库**：材料通常会给酒带来什么感官和气质。

匹配流程本身保持稳定，避免每增加一个想法就修改数据库结构和算法。

### 4.3 怎么判断效果是否变好

先选择一批自己熟悉的说唱歌曲和鸡尾酒进行测试，重点观察：

- 歌曲的一句话理解是否正确；
- 5～8 个标签是否抓住重点；
- 合适歌名能否进入前列；
- 三个推荐中是否至少有一个愿意使用；
- 哪些错误来自歌曲标签，哪些来自材料规则。

用户最终选择、跳过或修改了哪个名字，都应该记录下来，作为下一轮调整依据。

---

## 5. 第一版明确不做什么

- 不分析 Trap、Drill、Boom bap 等具体说唱流派；
- 不建立 valence-arousal 等情绪坐标；
- 不拆分七八个人格轴；
- 不要求每个感官维度都输出；
- 不为每个标签设计复杂的来源和置信度结构；
- 不建立向量知识库或复杂 RAG；
- 不根据歌名主观剔除歌曲；
- 不让 LLM 在每次起名时重新读取 100 首完整歌词。

## 6. 当前需要确认的问题

1. 四类共用标签是否足够：情绪、气质、感官、场景；
2. 每首歌和每杯酒最多 5～8 个标签是否合适；
3. 第一批共用标签词表应该包含哪些词；
4. 每次推荐三个歌名是否符合使用习惯。

这四个问题确认后，再进入 Prompt 和匹配权重的具体设计。
